# NeeDS フィジカルチェック アプリ 開発指示書

このドキュメントは、神戸のパーソナルトレーニングジム NeeDS のアスリート向け
フィジカルチェック・アプリを構築するための完全な仕様書です。
GitHub リポジトリの作成、実装、GitHub Pages での公開まで実行してください。

---

## 0. あなたに実行してほしいこと

1. 新しい GitHub リポジトリを作成する（`gh` CLI を使用）
   - リポジトリ名：`needs-physical-check`
   - Public
   - 説明：`NeeDS アスリート フィジカルチェック ダッシュボード`
2. 本仕様に沿って `index.html` を実装する（単一ファイル）
3. `README.md` にセットアップ手順を書く
4. commit / push する
5. GitHub Pages を有効化する（`gh api` でブランチ `main` / ルートを指定）
6. 公開URLをユーザーに提示する
7. Apps Script 側のコード（`apps-script/コード.gs`）もリポジトリに含める

ユーザーは GitHub の Web 画面での手作業を望んでいません。
ファイルのアップロード、ファイル名の変更、Pages の設定は
すべて CLI 側で完結させてください。

**ユーザーが手作業で行う必要があるのは、Apps Script のデプロイのみです。**
その手順は README に、初心者にも分かるレベルで詳細に書いてください。

## 1. このアプリの目的

紙の「NeeDSスコア記入用紙」をデジタル化し、
測定値を入力すると自動採点とダッシュボード表示まで行う。

対象は2種類：

- **体験者**（初回）：レーダーチャートで自分の身体の形と伸びしろを見せる。
  「このジムで身体を作りたい」と思わせる営業ツールとしての側面を持つ。
- **既存会員**（2回目以降）：推移グラフで変化を見せる管理ツール。

入力するのはトレーナー（タブレット想定）。見せる相手はアスリート本人。

## 2. システム構成

```
GitHub Pages（index.html 単一ファイル）
   ↓ fetch GET  → doGet   → 閾値取得 / 会員検索 / 履歴取得
   ↓ fetch POST → doPost  → 会員登録 / 測定保存
Apps Script（ウェブアプリとして公開）
   ↓
Google スプレッドシート（4シート）
   ├ members       会員マスタ
   ├ measurements  測定ログ
   ├ thresholds    閾値マスタ（ユーザーが編集する）
   └ rules         判定ルール（ユーザーが編集する）
```

### 重要な設計原則

**閾値をコードに埋め込まないこと。** `thresholds` / `rules` シートから
起動時に読み込む。ユーザーがスプレッドシートの数値を書き換えるだけで、
判定基準が変わる状態を維持する。これは必須要件。

### 接続設定について（今回の最重要ポイント）

前回の実装で、ユーザーは Apps Script のデプロイURLと合言葉を
アプリに入力する工程で強く詰まった。具体的な失敗：

- デプロイIDとウェブアプリURLを取り違えた
- URLの末尾に `?token=...&action=bootstrap` が付いたまま貼り付けた
- コードを変更したのにデプロイし直さず、古い版が動き続けた
- 「アクセスできるユーザー」が「Googleアカウントを持つ全員」で弾かれた

そのため、接続設定UIは次の要件を満たすこと：

- URL入力時に自動でサニタイズする（`?` 以降を削除、前後の空白を削除、
  末尾が `/exec` でなければ警告を出す）
- `AKfycb` で始まる文字列だけが貼られた場合（＝デプロイIDの誤貼り付け）を
  検知し、「これはデプロイIDです。ウェブアプリURLをコピーしてください」と
  明示的に伝える
- 接続失敗時は原因別のメッセージを出す
  （unauthorized→合言葉不一致とデプロイ未更新の両方を疑うよう案内、
    404→URL誤り、CORS→アクセス設定）
- 設定は localStorage に保存し、2回目以降は入力不要
- ヘッダーに「接続設定」ボタンを置き、いつでも開き直せるようにする

## 4. 採点ロジック

### 4-1. 共通原則

**未入力の項目は分母から除外する。** ゼロ点として平均に入れてはいけない。
体験時には一部項目しか測定しないため、これは必須。

### 4-2. 柔軟性

左右がある種目は、**低いほうの点数を種目スコアに採用する。**
柔軟性は制限がある側が問題になるため、平均ではなく低い側を採る。

これにより各部位が3種目・9点満点に揃う：

- 上半身：バンザイ（左右の低い方）、結帯（同）、肩関節外旋（同）
- 体幹部：体幹回旋（同）、体幹側屈（同）、ブリッジ
- 下半身：開脚、ASLR（同）、地面タッチ

**左右差は別途フラグを立てる（総合スコアには加算しない）：**

- 1点差 → 黄フラグ「左右差があります」
- 2点以上の差 → 赤フラグ「左右差が大きい」

### 4-3. 実測系（バランス・筋力・ジャンプ）

`thresholds` シートの `red_max` / `green_min` を参照し、1〜3点に変換する。

```
値 <= red_max        → 1点
値 >= green_min      → 3点
その間               → 2点
```

`direction` 列が `high` なら「高いほど良い」。現時点では全項目 high だが、
将来タイム系種目を追加する可能性があるため、`low` にも対応する実装にすること。

1RM系（`bp_1rm` / `sq_1rm` / `dl_1rm`）は、体重で割った比率を閾値と照合する。

### 4-4. カテゴリー得点率と色判定

```
得点率(%) = 入力済み項目の合計点 ÷ (入力済み項目数 × 3) × 100
```

色の境界（`rules` シートの値を使用）：

| 得点率 | 判定 | 色 |
|---|---|---|
| 88.9% 以上 | 緑 | #3B8F68 |
| 66.7% 以上 | 黄 | #D89A1F |
| 66.7% 未満 | 赤 | #C7453F |

これは「3種目9点満点で 8〜9点=緑、6〜7点=黄、0〜5点=赤」という
ユーザー指定の比率をそのまま一般化したもの。
柔軟性の部位別・全身、動きの質、その他すべてのカテゴリーに同じ比率を適用する。

**総合スコア**は、5カテゴリー（柔軟性・バランス・筋力・ジャンプ・動きの質）の
得点率を等重み平均する。重みは定数として外出しし、後から変更可能にすること。

筋力は体幹部・上半身・下半身の3つの小計も出す。

### 4-5. ジャンプの種目間分析

各ジャンプが何を表すか：

- **SQJ（反動なし）**：筋力そのものの強さ
- **CMJ（反動あり腕振りなし）**：下半身の反動・伸張反射（SSC）の活用度
- **ABJ（腕振りあり）**：腕振り・上半身からの連動性

**SQJ → CMJ の伸び率**（基準10%）：

| 伸び率 | 判定文 |
|---|---|
| 3%未満（ほぼ差なし） | 反動をほとんど使えていない。伸張反射が機能しておらず、筋力をそのまま跳躍に変換している状態。 |
| 3〜15% | 反動と筋力のバランスは標準的。 |
| 15%超 | 反動の使い方は上手いが筋力そのものが不足。SQJを引き上げればCMJも連動して伸びる。 |

**CMJ → ABJ の伸び率**（基準は5%と11%）：

| 伸び率 | 判定文 |
|---|---|
| 5%未満 | 腕振りと上半身の連動が機能していない。上半身の力を下半身に伝えられていない。 |
| 5〜11% | 標準的。 |
| 11%超 | 連動良好。同時にCMJ側にまだ伸びしろがある。 |

※ ABJは腕振りありのためCMJより高いのが正常。「連動不足＝伸び率が足りない」であり、
「ABJが低い」ではない点に注意（ユーザーの当初の説明は言い間違いで、この形が正）。

**SLCMJ（片脚）の判定 — 2軸で行う**：

1. **相対**：両脚CMJの50%が目標値。目標値の±5%以内なら達成。
   目標値の90%未満で赤（その側の片脚筋力または片脚での伸張反射が不十分）。
   例：CMJ 40cm → 目標20cm、19〜21cmが許容範囲。
2. **絶対値**：`thresholds` の `sl_cmj` 行で判定。
   相対だけだと「両脚とも弱いがバランスは良い」選手を見逃すため、両方見る。

**左右差**：高いほうを100とした差が10%以上で赤フラグ。
絶対値が高くても「改善が必要」と判定する。
対象：`sl_cmj` / `sl_sq` / `sl_stance` / `ground_touch_bal`

**RSI**：`hop_rsi` と `drop_rsi` の差が15%以上でフラグ。
どちらかが3.1以上なら「非常に良い」とテキスト表示（色は緑のまま）。

## 5. 閾値マスタ（thresholds シート）

添付の `NeeDS_閾値マスタ_v1.xlsx` を参照。64行（16項目 × 男女 × ジュニア/大人）。

列構成：

```
item_key | item_name | category | sex | age_band | unit | red_max | green_min | direction | source | note
```

- `sex`：`M` / `F`
- `age_band`：`adult`（17歳以上）/ `junior`（16歳以下）
- 将来 `elementary`（小学6年生以下）を追加できる構造にすること

### 確定値（ユーザー指定・成人男性）

| 項目 | red_max | green_min |
|---|---|---|
| ABJ | 39 | 55 |
| CMJ | 35 | 49 |
| SQJ | 31 | 44 |
| hop_rsi / drop_rsi | 1.89 | 2.6 |
| bp_1rm（体重比） | 0.80 | 1.21 |

CMJはABJの10%減、SQJはCMJのさらに10%減（端数切り捨て）というルールで算出済み。

### 仮置き値の係数根拠（文献ベース）

- 跳躍高：女性 = 男性 × 0.78
- RSI：女性 = 男性 × 0.80
- 跳躍高：ジュニア男子 = 成人男性 × 0.85 / ジュニア女子 = 成人女性 × 0.90
- 1RM上半身：女性 = 男性 × 0.65 / 1RM下半身：女性 = 男性 × 0.80
- 1RM：ジュニア = 成人 × 0.70
- 体幹持久（腹筋・プランク）：女性 = 男性 × 0.90

**片脚立位と地面タッチは NeeDS 独自プロトコルのため参照文献がなく、
仮置きの度合いが最も高い。**実測データが20〜30件たまった時点で、
その分布から引き直す前提。

## 7. データ構造

### members シート

```
member_id | name | kana | sex | birth_date | sport | registered_at | note
```

`member_id` は `NDS0001` 形式で自動発番。

**名前をキーにしないこと。** 表記ゆれ・同姓同名・改姓で履歴が分断されるため、
内部は必ず `member_id` で紐づける。UIは「名前を数文字入力→候補から選ぶ」形式にし、
操作感だけ「名前で呼び出す」ようにする。

### measurements シート（1行＝1回の測定）

```
【メタ】measurement_id | member_id | measured_at | session_no | age | age_band |
        height | weight | body_fat | lbm | injury | estimated_items | trainer | note
【柔軟】banzai_R ... ground_touch_flex（15列）
【バランス】sl_stance_R ... ground_touch_bal_L（4列）
【筋力】ab30s ... pl_basic（9列）
【ジャンプ】sqj ... drop_rsi（7列）
【動きの質】sq_quality ... rot_drill_low（5列）
【スコア】score_flex | score_balance | score_strength | score_jump |
         score_quality | score_total | risk_flags
```

- `age` / `age_band` / `lbm` / `session_no` は**サーバー側（Apps Script）で計算**する。
  アプリ側の計算違いが混入するのを防ぐため。
- **実測値とスコアの両方を保存する。** 閾値は将来必ず調整されるが、
  実測値が残っていれば表示時に現行ロジックで全回を再計算でき、
  推移グラフが基準変更で壊れない。保存済みスコアは「当時どう見せたか」の記録。

## 8. 画面構成

### 画面1：選手を選ぶ

- 名前の部分一致検索（インクリメンタル、debounce 250ms程度）
- 候補リストから選択 → 履歴を読み込んで画面2へ自動遷移
- 新規登録フォーム（氏名・かな・性別・生年月日・競技種目）
- 登録直後もそのまま画面2へ遷移

### 画面2：測定を入力

- 上部に測定日・身長・体重・体脂肪率・担当・怪我/障害
- 5つのタブ（柔軟性 / バランス / 筋力 / ジャンプ / 動きの質）で40項目
- 柔軟性と動きの質は 0〜3 のボタン、実測系は数値入力
- 1RM系には「推定」チェックボックス
- **触らなかった項目は空欄のまま採点対象外**
- 「採点して保存する」と「保存せず結果を見る」の2ボタン

### 画面3：結果を見る

構成順：

1. **レーダーチャート**（5カテゴリー、0〜100）を最上部に配置
   総合点を巨大表示するより、身体の「形」が見えるほうが
   どこを伸ばすべきかが伝わる。ただしこの主従関係は未確定で、
   ユーザーが実物を見て判断する予定。切り替えやすい実装にしておくこと。
2. 総合スコアとカテゴリー別バー
3. **ジャンプの中身**（SQJ→CMJ、CMJ→ABJ の伸び率と解説文、片脚の目標値）
4. **気をつけたい点**（左右差、片脚の目標未達、RSI差のフラグ）
5. **項目ごとの結果**（実測値と赤黄緑の判定）
6. **推移グラフ**（2回目以降のみ。1回目は「2回目から表示されます」と案内）

## 9. デザイン方針（前回決定済み・踏襲すること）

赤・黄・緑を計測機器の信号灯として機能させるため、
背景は無彩色に寄せ、信号色は彩度を落として臨床的に見せる。
ネオン系の暗色ダッシュボードは避ける。競技現場の計測票に近い落ち着いた見え方。

```
背景     #EDEEF0
パネル   #FFFFFF
文字     #16202B（インクネイビー）
補助文字 #5B6875
罫線     #D3D7DC
赤       #C7453F   赤背景 #F7E5E4
黄       #D89A1F   黄背景 #FAF0DC
緑       #3B8F68   緑背景 #E2F0E9
```

書体：数値は Archivo（等幅数字、`font-variant-numeric: tabular-nums`）、
