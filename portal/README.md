# アスチェック会員ポータル（開発中）

既存 index.html と独立した Next.js アプリ。一般用 physical-check のDBへ接続しない。
まだ本番利用・実会員データの移行は行わない。

## ローカル起動

Node.js 22以上、pnpmを使用する。このディレクトリで以下を実行。

```sh
pnpm install --frozen-lockfile
pnpm test:db
pnpm build
pnpm dev
```

接続設定なしではログイン画面が準備中となり、保護されたページはログインへ戻る。
`.env.example` を `.env.local` にコピーし、専用開発プロジェクトの設定をローカルで入力する。
秘密のキーはチャット・Git・ブラウザ向け変数へ貼らない。service roleキーはサーバー専用。

## 専用Supabase開発環境の接続手順

2026-10-17：専用開発DBへのSQL適用、ローカル接続設定、初期管理者の招待送信まで実施済み。
初回パスワード設定後、本人のChromeで管理者のスタッフ画面へのアクセスを確認済み。以下は再構築時の手順。

1. アスチェック専用プロジェクトを用意する。一般用と本番スプレッドシートは変更しない。
2. 空の開発DBへ `../supabase/migrations/0001_athlete_accounts.sql`、`0002_member_invitations.sql` の順に適用する。
3. Authのメール認証を有効にし、Site URLと許可するRedirect URLを開発ポータルのURLに設定する。公開時はHTTPSを使用する。
4. Invite userのメールテンプレートのリンクを次のようにする。

```html
<a href="{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&amp;type=invite">アカウントを設定する</a>
```

5. `.env.local` にURL、publishable key、service role key、SITE_URLを設定し再起動する。
6. 管理されたAuth管理画面で初期スタッフを作成し、DB管理画面で会社と `athlete_staff` の対応を登録する。会社ID・AuthユーザーIDを照合する。自己申告のmetadataでは権限を与えない。
7. 架空会員、測定、会社別基準を登録する。基準は既存CSVと照合する。基準未登録では総合点を表示しない。
8. 管理者のスタッフ画面から、利用許可を得たテストメールアドレスへ招待する。受信→パスワード設定→本人への紐付け→履歴表示を実環境で確認する。

初期管理者への招待メール送信は実施済み。招待の再送・失効管理画面、既存Authアカウントへの招待、パスワード再設定画面は未実装。現段階では運営担当者が確認して対応する。

## 現在できている範囲

- サーバーでユーザー検証するログイン・ログアウト、メール招待・初回パスワード設定の処理。
- スタッフの所属会社会員一覧、本人マイページの公開済み履歴・簡易結果・公開コメント。
- 会社・本人のRLS分離。内部メモは別テーブル。停止した会社・会員アクセスを拒否。
- 未対応の測定定義は再解釈せず表示を停止。

## 残る実装・検証

- 会員・測定の登録編集画面、過去記録移行、保存時採点の接続。
- 既存ボディマップ・レーダー・推移・説明を移植。現行の公開画面は変更していない。
- 項目と評価基準の管理画面、教材候補の確定・本人公開。
- 実Supabase上の認証・メール・Cookie更新・権限の通し確認。スマートフォンでログイン後画面を確認。

DBテストはPGliteのPostgreSQL上でAuthを模したユーザーと権限を使う。Supabase Auth自体の動作保証ではない。
履歴の現在の詳細画面は実測値を現行基準で計算する簡易版。当時の採点表示は未実装。
